## 2.3  Multi-task learning

_Argument order: what MTL is and why it can help -> the sharing spectrum (hard -> soft -> structured/routing) -> why it can hurt (negative transfer) -> the balancer family that tries to fix it -> the honest finding that balancers rarely beat tuned fixed weights -> MTL as used in mobility, and the gap the dissertation fills._

| # | Cite (key) | Sentence it supports |
|---|---|---|
| 1 | `caruana1997multitask` | Multi-task learning is inductive transfer: a representation shared across related tasks generalizes better than single-task training. **(defines MTL)** |
| 2 | `[new] ruder2017mtloverview` | Deep MTL is organized around two mechanisms, hard and soft parameter sharing, which frames the whole design space. **(defines hard vs soft sharing)** |
| 3 | `misra2016cross` | Cross-stitch units learn per-layer linear combinations of two task networks' activations, a canonical soft-sharing scheme. `[fix DOI -> 10.1109/CVPR.2016.433]` |
| 4 | `ma2018mmoe` | MMoE shares a pool of expert subnetworks but gives each task its own gating network, introducing routing to MTL. **(defines MoE routing)** |
| 5 | `[new] tang2020ple` | PLE/CGC explicitly separates shared from task-specific experts in layered gates, the structured-sharing topology the joint model descends from. → |
| 6 | `[new] hazimeh2021dselectk` | DSelect-k makes expert selection differentiable and sparse, completing the MMoE -> PLE -> DSelect-k routing arc. |
| 7 | `Zhang2020` | Negative transfer is the failure mode where joint training hurts a task relative to its single-task model, motivating balance. **(defines negative transfer)** |
| 8 | `[new] kendall2018uncertainty` | Task losses can be weighted automatically by each task's homoscedastic uncertainty, the first widely used loss balancer. **(defines loss weighting)** |
| 9 | `chen2018gradnorm` | GradNorm rescales per-task gradient magnitudes so tasks train at comparable rates. |
| 10 | `liu2019dwa` | Dynamic Weight Averaging sets task weights from the rate of loss change, a cheap schedule-based balancer. |
| 11 | `yu2020pcgrad` | PCGrad de-conflicts tasks by projecting each task gradient off any conflicting task's gradient. **(defines gradient conflict)** |
| 12 | `[new] liu2021cagrad` | CAGrad seeks an update close to the average gradient while minimizing conflict, with convergence guarantees. |
| 13 | `navon2022nashmtl` | Nash-MTL treats gradient combination as a bargaining game and uses the Nash solution as the joint direction. |
| 14 | `senushkin2023aligned` | Aligned-MTL aligns principal gradient components and uses the gradient system's condition number as a stability criterion. |
| 15 | `liu2023famo` | FAMO balances loss decreases in O(1) time and space, avoiding per-step access to all task gradients. |
| 16 | `[new] lin2022rlw` | Random weighting is a competitive baseline, a litmus test suggesting elaborate balancers often do not beat simple ones. → |
| 17 | `xin2022domtl` | A controlled study finds current MTL optimization methods frequently fail to beat a well-tuned fixed-weight baseline, the honest position the dissertation adopts. |
| 18 | `vandenhende2022mtl` | A dense-prediction survey consolidates architectures and optimization for MTL and frames when sharing helps. **(survey anchor)** |
| 19 | `Liao2018` | In mobility, MCARNN jointly predicts activity and next **place** with a context-aware recurrent unit (parallel MTL). **(MTL-for-mobility begins)** |
| 20 | `huang2024cslsl` | CSLSL uses a causal cascade (time -> activity -> location) so category/activity is an intermediate step toward next **place**. **(cascade lineage)** |
| 21 | `silva2025mtlnet` | The project's own starting point (MTLnet) shows naive hard sharing on a place-level embedding does not beat single-task models, setting up the representation argument. **(project record)** |
